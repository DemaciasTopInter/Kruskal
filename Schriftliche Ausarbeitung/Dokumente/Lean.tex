\subsection{Was ist Lean}\todo{sub\-section Lean}
Lean\cite{10.1007/978-3-030-79876-5_37} ist beides eine funktionale Progammiersprache und ein Beweis Assistent für formale Beweise.
Das Projekt wurde 2013 von Leonardo de Moura und Sebastian Ullrich ins Leben gerufen.
Die aktuelle Version Lean 4 ist selbst in Lean geschrieben und wurde im September 2023 released.

Lean basiert stark auf seinem Typen-System
Dieses ordnet jedem Term in Lean einen Typ zu, welcher wiederum selbst ein Term ist.
Hier ein par Beispiele:
\begin{lstlisting}
"Hello World!" : String
16 : Nat
{ val := 16, isLt := by omega } : Fin 32
16 < 32 : Prop
isLt : 16 < 32
Nat : Type
Prop : Type
Fin : Nat → Type
Type : Type 1
Type 1 : Type 2
\end{lstlisting}
Ein String ist eine Zeichenkette und Nat oder auch $\mathbb{N}$ eine natürliche Zahl.
Fin n mit einer natürlichen Zahl n ist die Menge der natürlichen Zahlen, die kleiner als n sind.
Ein Element von Fin n besteht zum einen aus einer Zahl val und zum anderen aus einem Nachweis isLt, dass val kleiner als n ist.
Thesen (engl. Propositions) sind vom Typ Prop.
Dabei ist jede These selbst wider ein Typ und die Elemente dieses Typs sind die Beweise, die sie belegen.
Was Thesen von anderen Typen unterseidet, ist, dass alle ihre Elemente gleich sind.
Es macht für Lean keinen Unterschied, wie eine These bewiesen wurde, solange es mindestens einen Beweis gibt.
Alle Typen wie String, Nat, Fin 32 oder Prop haben den Typ Type.
Auch Funktionen haben Typen, nämlich den von wo nach wo sie abbilden.
Fin ist zum Beispiel vom Typ der Funktionen, die von Nat auf Type abbilden.
Da in Lean alles einen Typ hat, gilt das auch Type.
Type, was das gleiche ist wie Type 0, ist vom Typ Type 1.
Type 1 ist wiederum vom Typ Type 2 und so weiter.
Es gibt in Lean auf die weise unendlich viele Typ-Universen.

Um eigene Typen und Funktionen definieren, gibt es in Lean verschiedene Möglichkeiten:
Mit \textbf{def} oder \textbf{abbrev} lassen sich vor allem Funktionen definieren, aber auch konstante Elemente eines Typs oder einfache zusammen gesetzte Typen, wie zum Beispiel Tupel.
Der Hauptunterschied dabei ist, dass aus sicht von Lean def etwas neues kreiert über das noch nichts bekannt ist, wärend abbrev eher ein Alias mit neuem Namen erzeugt.
Komplexere Typen lassen sich als \textbf{structure} definieren was an Klassen aus dem objektorientierten Progammieren erinnert mit beliebig vielen Atributen und Methoden.
\begin{lstlisting}
def myType : Type := Nat × String

def f (x : Nat) : Nat := 3*x^2 - 4*x + 5

structure edge : Type where
  node1 : Nat
  node2 : Nat
  nodesLt : node1 < node2
\end{lstlisting}
Mit \textbf{inductive} lassen sich induktive Typen definieren.
Über diese lassen sich dann auch Induktionen führen.
Die häfigsten Beispiele dafür sind die natürlichen Zahlen und Listen.
\begin{lstlisting}
inductive myNat : Type where
  | zero : myNat α
  | succ (n : myNat α) : myNat α

inductive myList (α : Type) : Type where
  | nil : myList α
  | cons (head : α) (tail : myList α) : myList α
\end{lstlisting}

Wenn Funktionen für mehrere Typen definiert sein sollen (Polymorphie), geht das entweder, indem der Typ ein ein Argument der Funktion ist, oder über Typ-Klassen (Ad-hoc Polymorphie).
Letztere empfehlen sich vor allem dann, wenn sich die Funktion je nach Typ anders verhallten und beliebig erweiterbar sein soll.
Klassen werden mit \textbf{class} oder \textbf{class inductive} definiert werden, was dann so aussieht, wie bei structure oder inductive.
Dabei sind dann die Funktionen, die für alle Typen dieser Klasse definiert sein sollen, in der Klasse deklariet aber nicht definiert.
Wie diese Funktionen für den einzelnen Typen definiert sein sollen ist ja individuell.

Damit ein Typ nun Teil einer Klasse werden kann, muss für ihn eine Instanz erstellt werden, in der definiert ist, wie sich jede einzelne Funktion für ihn verhält.

Häufige Beispiele für einfache Klassen mit je nur einer Funktion sind arithmetische Operatoren die ja zu Beispiel auf Nat, Int, Float, Fin und weiteren definiert sein müssen.

Ein Beispiel für eine komplexere Klasse wäre zum Beispiel eine Gruppe:
\begin{lstlisting}
class Group (α : Type) (add : α → α → α) where
  e : α
  add_assoc (a b c : α) : add (add a b) c = add a (add b c)
  ex_nutral : ∀ (a : α), add a e = a
  ex_invers : ∀ (a : α), ∃ (h : α), add a h = e

instance int_Group : Group Int Add.add where
  e := 0
  add_assoc := Int.add_assoc
  ex_nutral := Int.add_zero
  ex_invers := by
    intro a
    refine ⟨-a, by grind⟩
\end{lstlisting}\todo{Fällt mir noch was besseres ein?}

Mit \textbf{theorem} (oder wenn man die Mathlib Bibliothek verwendet, äquivalent mit \textbf{lemma}) lassen sich Beweise für Aussagen definieren.
Das ähnelt vom Aufbau her der Definition mit def nur das der Typ jetzt die Aussage ist.

Es gibt drei arten von Argumenten, die bei einer Definition angegeben werden können:
\begin{itemize}
  \item In runden Klammern stehen die normalen Argumente, die beim Aufruf übergeben werden müssen.
        Sie weredn geschrieben als ein oder mehrere Namen gefolgt von einem Doppelpunkt und dem Typ.
  \item In geschweiften Klammern stehen implezite Argumente
        Sie haben den selben Aufbau, werden aber im Regelfall nicht mit übergeben.
  \item In eckigen Klammern stehen Bedingungen an Klassenzugehörigkeiten.
        Sie bekommen in der Regel keine Namen, besthehen also nur aus ihrer Aussage.
        Sie müssen auch nicht übergeben werden.
        Es reicht, dass eine Instanz existiert.
\end{itemize}
Ein Beispiel, wo alle drei vorkommen wäre diese Lemma, das besagt, dass eine Listevon beliebigem Typ kürzer wird, wenn man eines ihrer Elemente rausfiltert:
\begin{lstlisting}
theorem length_of_filter_mem {α : Type} {l : List α} {a : α} [DecidableEq α] (h_mem : a ∈ l) : l.length ≥ 1 + (l.filter (fun b => b ≠ a)).length := by …
\end{lstlisting}
In dem Nachweis h\_mem, dass das Element a in der Liste l enthalten ist, sind a, l und der Typ $\alpha$ implizit enthalten.
Es reicht also den Beweis h\_mem zu übergeben, wenn man dieses Lemma nutzen möchte,
sofern es für den entsprechenden Typ eine Instanz der Klasse DecidableEq gibt, also für zwei Elemente entscheidbar ist, ob sie gleich sind.

% Der Taktik Modus und das Laufen beim Schreiben
Der Beweis für eine Aussage passiert dann im Taktik Modus, einer interaktiven Beweisumgebung.
Diese wird durch \textbf{by} nach dem := geöffnet.
Im Kontext des Taktik Modus befinden sich die aktuellen lokalen Konstanten und Hypothesen sowie das Ziel, das durch $\vdash$ gekennzeichnet ist.
Diese können nun mit Taktiken Stück für Stück verändert und angepasst werden, bis das das Ziel geschlossen ist.
Dabei kann es auch vorkommen, dass zwischenzeitlich weitere Ziele geöffnet werden, diese müssen in dem Fall alle der Reihe nach geschlossen werden, damit die Aussage bewiesen ist.

Lean hat die Besonderheit, das es den Code bereits beim schreiben auswertet und mitlaufen lässt und einem so immer den aktuelln Zustand des Kontextes im Editor anzeigt.
In Abbildung \ref{leaninvscode} kann man das in aktion sehen.

Die von mir am häufigsten verwendeten Taktiken stelle ich im folgenden einmal kurz vor.

Die Taktik \textbf{rw} (kurz für rewrite) nimmt als Argument eine Liste von Gleichungen, also eine Aussagen der Form $x = y$ und ersetzt im Ziel dann alle Vorkommen von Term $x$ durch Term $y$.
Alternativ ersetzt die Taktik \textbf{nth\_rewrite} nur des n-te Vorkommen.

Die Taktik \textbf{apply} funktioniert so ähnlich und nimmt als Argument eine Aussage der Form $a \rightarrow b$.
War das Ziel ein Beweis für Aussage $b$, ist nun das neue Ziel ein Beweis für Aussage $a$.

Die nächsten zwei Taktiken sind Automatisationen, die einem Beweisarbeit abnehmen.
\textbf{simp} versucht das Ziel so weit es geht zu vereinfachen und tut dies quasi durch wiederholtes Verwenden von rw.
Dafür nimmt sie wie rw als Argument eine Liste von Gleichungen, allerdings probiert sie auch alle bereits existierenden Beweise, die mit dem Tag simp markiert wurden.
Davon gibt es in Lean schon von Haus aus viele, aber durch Bibliotheken, wie zum Beispiel Mathlib, oder auch eigene Theoreme kommen noch mehr hinzu.
Mit dem optionalen Argument only kann man dafür sorgen, dass nur die übergebenen Gleichungen verwendet werden.
Es gibt auch die option nur einzelne Gleichungen auszuschließen, indem man sie in der Liste mit aufführt und je ein Minus davor schreibt.
rw und simp lassen sich ausßerdem mit dem Zusatz \textbf{at} auch auf eine oder mehrere Hypothesen anwenden.

Ein Beispiel, wie man mit den Gleichungen h1 und h2 die Aussagen h3, h4 und h5 vereinfachen würde:
\begin{lstlisting}
simp [h1, h2] at h3 h4 h5
\end{lstlisting}

Die andere Automatisierung ist \textbf{grind}.
Sie ist von modernen SMT Solvern inspiriert und versucht ein Ziel zu schließen, indem sie aus allen bekanten Fakten immer weitere Fakten ableitet und dabei hofft auf einen Widerspruch zu stoßen.

Die Taktiken \textbf{let} und \textbf{have} sind die lokalen Varianten von def und theorem. 
Mit let können lokale Konstanten und Funktionen definiert werden und mit have quasi lokale Hilfslemma.
Diese müssen natürlich auch erst einmal bewiesen werden und erzeugen ein vorrangiges Ziel, das zuerst geschlossenwerden muss, bevor es im eigentlichen Ziel weiter geht.

Mit der Taktik \textbf{intro} kann eine Bedingung aus dem dem Ziel holen und als Konstante oder Hypothese in den Kontext aufnehmen.
Als Argument nimmt sie den Namen, den das Element dann bekommt.
Aus dem Ziel $a \rightarrow b$ wird dann durch intro h die neue Hypothese $h : a$ angelegt und das Ziel ist dann nurnoch $b$.
Man kan auch mehrere Namen angeben, was den Effekt hat, als würde man intro mehrmals hinter einander aufrufen.

\textbf{revert} ist die Umkehrfunktion von intro.
Sie nimmt als Argument einen oder mehrere Namen und fügt die entsprechenden Elemente als Bedingungen dem Ziel hinzu.

Es gibt verschiedene Möglichkeiten für Fallunterscheidungen.
Die Taktik \textbf{by\-\_cases} zusammen mit einer Aussage spaltet das Ziel in in zwei Unterziele.
Im ersten ist die Aussage als Hypothese im Kontext und im zweiten ihre Negation.

Eine \textbf{induktion} lässt sich anwenden, wenn man im Kontext ein Element mit einem induktiven Typ hat,
häufig eine natürliche Zahl oder eine Liste, oder wenn man eine Aussage über eine rekursive Funktion trifft.
Sie teilt das Ziel in ein Unterziel pro Fall, den das Element annehmen kann und stellt in den Nicht-Basisfällen eine entsprechende Induktionshpothese zur verfügung.
So ähnlich funktioniert auch \textbf{cases} welche für ein Element mit einem induktiven Typ das Ziel anhand der möglichen Fälle aufspaltet, allerdings ohne eine Induktionshpothese.

Die Taktik \textbf{rcases} kann eine Hypothese beliebig fein in ihre Einzelteile aufteilen.
Sie kann aus einen $\exists$ ein spezifisches Element machen, eine $\land$-Aussage in zwei einzelne Hypothesen aufteilen
und aus einer $\lor$-Aussage zwei Unterziele erzeugen in denen je die eine oder die andere Aussage als Hypothese existiert.
Diese Taktik benutze ich zum Beispiel häufiger um eine Existenzaussage in ihre Einzelteile zu zerlegen.
Das sieht dann zum Beispiel so aus:
\begin{lstlisting}
-- Kontext vorher
id : Nat
nodeList : List node
h : ∃ x ∈ nodeList, x.id = id
--
rcases h with ⟨x, h_x_in, h_eq⟩
-- Kontext danach
id : Nat
nodeList : List node
x : node
h_x_in : x ∈ nodeList
h_eq : x.id = id
--
\end{lstlisting}

Hat das Ziel die Form $a \lor b$ reicht es eine der beiden Aussagen zu zeigen.
\textbf{left} und \textbf{right} machen aus dem Ziel dann nurnoch $a$ bzw. nurnoch $b$.

Hat das Ziel hingegen die Form $a \land b$ müssen beide Aussagen gezeigt werden.
Die Taktik \textbf{constructor} spaltet das Ziel dann in zwei Ziele auf, die dann nacheinander gelöst werden müssen.

\textbf{refine} und \textbf{exact} sind beides Taktiken um ein Ziel zu schließen.
Hat man es durch Umformungen von Ziel und Hypothese geschafft, dass eine Hypothese h genau das aussagt, was im Ziel steht, kann man es mit exact h schließen.
hat man hingegen nur Teile der Aussage, kann man stattdessen refine benutzen, welche dann das Ziel schließt, aber für jede Lücke wieder ein Ziel öffnet.

Keine Taktik aber auch ganz nützlich sind die Platzhalte \textbf{\_} und \textbf{?\_}.
Überall wo ein Beweis als grgument gefordert ist, kann stattdessen auch ?\_ angegeben werden, was bedeutet, dass man den beweis nachreicht.
Der Beweis wird also als weiteres Ziel geöffnet, um das man sich dann kümmert, wenn man das aktuelle geschlossen hat.
Das ist auch mit Lücke bei refine gemeint.
Hingegen kann man \_ überall da anwenden, wo das zu ersetzende aus dem Zusammenhang eindeutig impliziert wird.
Zum Beispiel leifert die Funktion List.choose das erste Element einer Liste, das eine gegebene Bedingung erfüllt.
Dafür fordert sie als Argumente die Bedingung p, die Liste l und einen Nachweis hp, dass es auch ein solches Element gibt.
\begin{lstlisting}
def List.choose (p : α → Prop) [DecidablePred p] (l : List α) (hp : ∃ a, a ∈ l ∧ p a) : α
\end{lstlisting}
Wenn man die Hypothese hp jetzt schon im Kontext hat ist ja automatisch klar, welche Liste l und Bedingung p gemeint sind, das sie ja schon in der Aussage stecken.
Es reicht also beim Funktionsaufruf hp mitzugeben:
\begin{lstlisting}
let x : α := List.choose _ _ hp
\end{lstlisting}

\subsection{Anwendung}\todo{sub\-section Anwendung}
Microsoft nutzt Lean um nachweislich sichere Kryptographie zu Produzieren.
Wie in diesem Bolg-Post\cite{microsoftresearchblog} eines Microsoft-Research-Teams zu lesen, nutzt Microsoft Lean um die Einhaltung von Standarts zu verifizieren.
Da in der Kryptographie der Code häufig sehr hardwarenah und architekturabhängig geschrieben wird
und Laufzeitoptimirungen enthält sieht er selten genau so aus, wie der Algorithmus aus dem Standart.
Um hierbei sicher zu gehen, dass die Funktionsweise immer noch die gleiche ist, reicht Testen nicht immer aus, da ein kleiner Fehler die Sicherheit des gesamten Systhems untergraben kann.
Deshalb formalizieren sie die Standarts in Lean.
Eine Implementation in Rust wird dann auf eine äquivalente Implementatierung in Lean abgebildet.
Der Vorteil gegenüber dem Testen ist, dass nun bewiesen werden kann, dass für alle möglichen Inputs, die eventuelle Vorbedingungen erfüllen, auch ein korrekter Output erzeugt wird.
Wohingegen Testen immer nur für begrenzt viele Inputs zeigen kann, dass der Output korrekt ist.

\subsection{Lean und KI}\todo{sub\-section KI}

Sobalt das mathematische Problem formaliziert wurde, kann KI versuchen es zu lösen.
Oder wenn bereits ein Beweis bekannt ist, kann KI probieren einen einfacheren oder schnelleren zuu finden.

In \cite{microsoftresearchblog} wird erklärt, wie KI bereits zum Einsatz kommt und welche Aufgaben sie übernimmt.
Zum einen das Übersetzen von Standarts in Lean Spezifikationen.
Diese müssen natürlich getestet und von Menschen geprüft werden, spraren unterm Strich aber trozdem Arbeit.
Zum anderen beim automatischen Schreiben und Aktualisieren von Beweisen.
Das Schöne ist, das Lean garantiert, dass ein Beweis auch funktioniert, sofer also der Fehler nicht schon in der Formulierung der zu beweisenden Aussage liegt,
kann ein Beweis, der von einer KI geschrieben wurde, nicht fälschlich positiv Sein.
Menschen müssen nur die Beweise per Hand schreiben, bei denen die KI scheitert.
